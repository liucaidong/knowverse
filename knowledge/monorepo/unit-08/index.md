# 08 · 工具选型：pnpm、Turbo、Nx、Rush

> 来源说明：根据历史对话与官方文档归纳编写的独立教材，不是原始聊天逐字转录。技术事实以校对日期与项目实际版本为准。

## 我们不做没有前提的冠军榜

pnpm Workspace 是**工作区与包管理基础**，Turborepo 偏重任务编排与缓存，Nx 强于项目图、受影响任务、约束与云端能力，Rush 偏组织治理、版本与发布流程。几者不在同一层上，不应该用「五个工具谁最强」的标题直接做结论。

| 典型约束 | 先考察 | 为什么 |
|---|---|---|
| 5—10 个包、少量 CI | pnpm alone | 少引入一层工具成本 |
| CI 构建重复、输入输出清晰 | Turbo | 声明任务图与缓存就可能收益明显 |
| 依赖可视化、模块边界、精细 affected | Nx | 项目图和任务级 affected 是重要区分点 |
| 大规模团队、发布审计、复杂版本策略 | Rush | 治理流程收益更大 |

这是工程判断的**起点**，不是特性保证。具体方案还要衡量版本成熟度、团队技能、构建缓存命中率、跨端兼容成本和迁移锁定。

## 2026 的关键变化：Nx 24

Nx 24 的 task-based affected 默认策略与旧版的 project-based affected 不同。旧仓库升级可能仍保留兼容模式。由于影响任务的输入定义会决定是否跳过工作，验证工具时必须显式构造三个修改样本：`src/*.ts`、`test/*.test.ts`、根配置文件。比较实际选中的 build、test、lint，而不是只看一个「affected 项目总数」。

## 一个可复现的 POC

设定 5 包示例图（contracts、domain、web、mobile、api），为每个工具写同样的任务：类型检查、单元测试、产物构建。准备固定修改集：改 `contracts`、改 `domain` 的测试、改 `web` CSS、改锁文件。分别记录：

1. **正确性**：该重跑的任务是否重跑，该复用的产物是否可恢复。
2. **性能**：冷启动、热缓存、跨分支、跨 CI worker 的耗时。
3. **治理**：非法跨包 import 是否被阻止，发布计划可否审计。
4. **可迁移性**：是否需要换项目结构、改几十份配置才能退出。

不要把空仓库微基准测试的结果推广到 150 包的生产仓库；也不要仅根据营销功能列表就假设缓存正确。

## 保留 Rush 的条件结论

如果实际组织需要集中依赖治理、复杂版本策略、审核公开发布并且愿意投入工具维护，Rush 可能更适合。如果首要痛点是「看不清依赖关系」和「想先把 affected 跑对」，Nx 或更简单的自建边界检查通常更直接。工具选型是持续可审计的选择，不是一次无法推翻的信仰。
