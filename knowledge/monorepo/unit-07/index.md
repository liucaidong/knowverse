# 07 · Rush 治理：从单仓编排到组织契约

> 来源说明：根据历史对话与官方文档归纳编写的独立教材，不是原始聊天逐字转录。技术事实以校对日期与项目实际版本为准。

## 为什么有些组织选择 Rush

在仓库包数量多、应用团队独立、发布节奏不同、需要审计变更的组织里，单纯「有一条快的 build 命令」不足以解决问题。真正昂贵的是依赖失控、版本策略不一致、发布流水线不透明和变更责任缺失。Rush 的设计偏向集中规定规则，让跨项目操作有统一的流程入口。

本专题保留历史讨论的结论：**Rush 是有前提的倾向，不是所有仓库的首选**。当团队规模、包数量、发布审计要求确实能抵消治理成本时，Rush 才可能成为合理选择。

## 三种经常被误解的能力

1. **安装管理**：Rush 可以管理其下的 pnpm 配置、锁版本和一致性策略；它不等于用一个独立魔法安装器替代 npm 生态。
2. **增量构建 / 缓存**：`rush build` 可以利用输入状态跳过无需重做的构建；启用 build cache 后可从保存的产物恢复。两者不同。
3. **发布治理**：公开包的变更文件、版本策略、发布动作有一条可审计的链路；不是 `rush publish` 永远安全地自动推送。

## 发布闭环：change → version → publish

`rush change` 为公开包的变化登记类型与描述；维护者或 CI 可以用 `rush change --verify` 约束缺失的变更文件。版本整理过程考虑 change files 和 version policy；`rush publish` 支持只读预览及显式发布行为。具体命令组合和权限要按官方版本文档配置，并且发布步骤应要求独立审批，不能仅凭 `main` 新提交就自动发布。

```text
开发者改公共 API
   ↓
登记 changelog / semver 影响
   ↓
CI 验证变更文件与依赖一致性
   ↓
版本变更预览 / review
   ↓
打包、验签、发布和回滚证据
```

## 构建缓存的可信边界

假设一个 `react-native` 包的构建输出依赖 Xcode 配置、Hermes 版本、环境变量和 CodeGen 输入。如果缓存键只包含 JavaScript 文件，那么跨机器恢复的产物可能不可用。先把构建描述完整，才能讨论远端缓存与 Cobuild。远端缓存的共享策略还要考虑谁可以写缓存、是否可以由不可信 PR 污染、产物是否含敏感数据。

## 与 Nx 的正确比较

Nx 的项目图和边界规则更容易直接回答「谁依赖谁」，也有基于任务输入的 affected 能力；Rush 偏整体工程治理和发布纪律。两者并不在每一个维度直接对应同一种实现。比较时把「哪一层解决什么」拆开，避免把偏好当作功能事实。
