# 05 · 任务图、增量构建与缓存键

> 来源说明：根据历史对话与官方文档归纳编写的独立教材，不是原始聊天逐字转录。技术事实以校对日期与项目实际版本为准。

## 区分三种加速

**增量跳过**：本地已经构建过，且任务输入没有变化，直接跳过（可能需要原输出还在）。**缓存恢复**：输入相同，系统从本地或远端保存的产物重新解包，无须实际构建。**远端分布式执行**：任务交给其它工作节点，扩展并发能力。这三种优化经常被混为一个功能，实际上对稳定性、存储、权限和调度要求完全不同。

Rush 官方说明中，增量分析与 build cache 是两个不同机制：前者判断本地输出可否保留，后者缓存构建产物以便跨分支或机器恢复。Turbo 和 Nx 也通过明确 `inputs`、`outputs`、任务依赖等机制管理缓存。

## 缓存键是正确性的数学约定

可以抽象为：

\[K = H(\text{source},\text{lockfile},\text{task config},\text{env},\text{toolchain},\text{upstream outputs})\]

如果一个影响结果的输入不在哈希里，就可能出现**错误的缓存命中**。例如构建读取 `FEATURE_MODE`，但缓存输入只包含源文件；切换 `FEATURE_MODE` 后任务仍从旧缓存恢复，页面功能与预期不一致。

```text
输入集合未变 → 可以尝试缓存恢复
输入集合变化 → 必须重新计算对应任务
输出声明不完整 → 即便缓存键正确，也可能恢复不完整构建产物
```

**提示**：生产级缓存键还必须处理路径规范化、配置继承、命令参数、操作系统相关性和依赖任务产物。网页实验里的简化哈希仅用于教学，不是可复制的生产缓存实现。

## 任务依赖不等于受影响传播

例如 `web:build` 依赖 `contracts:build` 完成，这只是调度前置条件。是否因为 `contracts` 代码变化而重新执行 `web:build`，还需要看 `web:build` 的输入是否包含了上游代码/产物。在 Nx 24 的 task-based affected 里，官方特别强调：**`dependsOn` 本身不会使任务被判定为 affected**。这是依赖图、任务图、输入图的关键区别。

## 反直觉案例：测试修改影响 build 吗？

修改 `packages/domain/test/calculation.test.ts`：包级 affected 可能粗粒度地选择 `domain` 及其消费者的全部任务；任务级 affected 在正确配置 `inputs` 的前提下，可以只重跑测试而跳过产物不变的 build。这种精确性有代价：如果 `build` 隐式读取测试快照却未声明，跳过反而是错误。

## 实验任务

进入「缓存键实验台」，先让 `MODE` 不纳入键，构建一次 `MODE=A` 后切换 `MODE=B` 并重跑。观察错误复用；再把环境变量纳入键，确认必须重新构建。
