Rush 治理落地：什么时候值得引入

前提：不要把规模想象成需求

一个 5 包仓库、所有包都不公开发布、CI 只需几分钟，直接引入 Rush 可能只会制造配置与学习负担。相反，当仓库已经达到几十到数百包、存在多个团队、统一锁定依赖版本、要求审计 change files 或分支发布，Rush 的集中治理才可能创造超过维护成本的收益。历史讨论中的倾向「Rush（有前提）」本来就应理解为这个条件句，而不是全体仓库的固定答案。

第一阶段：只做可测量的治理

在迁移 Rush 之前记录一个基线：跨包改动平均牵涉几个项目、每周幽灵依赖数量、单次冷构建与增量构建耗时、重复版本冲突数量、公开发包失败与回滚次数。首先保证每个 package 的依赖声明准确；没有准确依赖图时，任何编排器都会被迫补偿不一致的事实。

第二阶段：版本一致性与发布策略

Rush 官方推荐的一致性检查可以帮助团队识别同一依赖被不同项目使用不兼容版本的情况，但这不意味着永远只能有一个版本；有些迁移必须采用受控的替代版本策略。对于公开包，先明确 lockstep / independent 等版本策略，配合 change files 和审核流程；对仅供仓库内使用的私有包，未必需要完整 npm 发布流程。

代码和契约变更
   ↓
公共包变更文件（说明 major/minor/patch）
   ↓
CI 规则验证 + 影响分析 + 构建测试
   ↓
版本计划预览 / 审核
   ↓
正式发布 / 留存产物 / 可回滚

rush change 为变更提供结构化证据，rush change --verify 可检查需要变更文件的修改。rush version、rush publish 的行为应按仓库版本策略和实际命令文档配置；绝不能把只读预览与带发布开关的真正发布混为一谈。

第三阶段：构建缓存

把 rush build 在本机基于输入跳过任务，与从存储恢复历史产物的 build cache 分开测试。启用缓存前先检查 outputs 是否完整、是否包含平台特异产物、源码生成输入是否已声明以及缓存写入是否可信。不可信 PR 贡献者不应获得可以污染受保护分支缓存的权限；缓存档案不应含令牌、私钥和未脱敏个人数据。

第四阶段：组织规则与 Agent

将仓库规则写到 AGENTS.md 是好的入口，但它必须关联到可执行检查：禁止底层依赖顶层、公开 API 破坏时的版本更新、受影响端的真实 bundle、构建缓存验证。只有 CI 可以独立验证这些规则，Agent 才能依据同一验收契约完成任务；否则规则会变成仅供阅读的文档。

引入失败的退出条件

连续两个月开发者平均改动耗时明显增加，而构建时间、发包正确率、依赖冲突指标没有改善；或者工具更新频繁需要大量手动修改。这时应回到能力清单，保留有价值的边界规则与测试，将任务图编排恢复为较轻的 pnpm 或其它方案。避免为了证明选型正确而隐藏成本。
